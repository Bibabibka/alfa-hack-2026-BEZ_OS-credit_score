# PD-скоринг заявок МСП

Модуль оценки вероятности дефолта (PD) для прототипа «Умный кредитный кабинет предпринимателя»: генератор синтетических данных, обучение модели с калибровкой, объяснение причин и решение по PD.

> Все данные синтетические, модель демонстрационная. Метка дефолта сгенерирована из заданной формулы, поэтому метрики показывают, что пайплайн работает, а не качество на реальном портфеле. В продукте модель нужно перекалибровать на данных банка.

## Состав

| Файл                      | Назначение                                                                       |
|---------------------------|----------------------------------------------------------------------------------|
| `generate_sme_dataset.py` | Генерирует датасет                                                               |
| `data/README.md`          | Подробное описание выборки: как она генерировалась и что означает каждый столбец |
| `pd_model.py`             | Признаки, пайплайны моделей, калибровка, причины решения, матрица решений        |
| `model_s.py`              | Обучает и сравнивает модели, сохраняет выбранную в `models/`                     |
| `models/pd_model.joblib`  | Обученная модель для сервиса                                                     |
| `models/model_card.json`  | Метрики, пороги, список признаков, версии                                        |


Настройки обучения лежат в константах вверху `train_pd_model.py`: `CHOSEN_MODEL` (`logreg` или `lightgbm`), `CHOSEN_CALIBRATION` (`platt` или `isotonic`), `POLICY` (пороги PD), `SPLIT` (доли выборок), `SEED`.

## Как это работает

1. **Данные.** Генератор создаёт 10 000 заявок: профиль бизнеса, параметры кредита, моки БКИ и ЕГРЮЛ, залог. Метка дефолта получается из логит-модели со скрытым фактором и шумом, средняя доля дефолтов около 8%.
2. **Разбиение.** 60% обучение, 20% калибровка, 20% тест, стратифицированно по метке.
3. **Базовая модель.** Логистическая регрессия (пропуски заполняются медианой с индикатором, признаки стандартизируются, категории кодируются one-hot) либо LightGBM (пропуски обрабатывает сам).
4. **Калибровка.** Выход базовой модели не является честной вероятностью. Поэтому на отдельной выборке обучается калибратор: Platt (логистическая регрессия поверх логита скора) или isotonic (монотонная ступенчатая функция). После этого `predict_pd` возвращает вероятность дефолта, пригодную для порогов.
5. **Причины.** `explain` считает вклад каждого признака в логит риска (для логрегрессии коэффициент на значение признака, для LightGBM `pred_contrib`), складывает вклады one-hot колонок обратно в исходный признак и возвращает топ-3 причины, повышающие риск, с готовыми текстами для кабинета.
6. **Решение.** `decide` переводит PD в решение по порогам:

| PD | Решение |
|---|---|
| до 4% | `approve` (одобрить на запрошенных условиях) |
| 4–8% | `counter_offer` (встречное предложение: сумма, срок, продукт) |
| 8–15% | `manual_review` (ручная проверка или запрос данных) |
| выше 15% | `reject` (отказ) |

Скоринг не принимает решение сам: stop-правила (ликвидация по ЕГРЮЛ, просрочка свыше 90 дней по БКИ) проверяются до модели, а итоговое решение учитывает также продукт, сумму и политику банка. Пороги в `POLICY` это бизнес-параметры, их подбирают по допустимому уровню риска.


## Ограничения

- **LightGBM не проверялся** в среде, где готовился код (библиотека недоступна); логрегрессия проверена полностью.
- **Isotonic на малой калибровочной выборке** (2 000 строк) даёт ступенчатые оценки и PD около 100% в хвосте, поэтому по умолчанию стоит Platt. Isotonic имеет смысл при существенно большей выборке.
- **Данные синтетические**, связи линейные и заданы нами, распределения не откалиброваны по статистике банка.
- **Дисбаланс** (около 8% дефолтов) учитывается калибровкой, взвешивание классов не используется; оценивайте AUC, KS, Brier и калибровку по децилям, а не accuracy.
- **Внешние источники** (ЕГРЮЛ/ЕГРИП, БКИ, ФНС, внутренние данные банка) смоделированы, это нужно указать в `THIRD_PARTY_NOTICES`.
